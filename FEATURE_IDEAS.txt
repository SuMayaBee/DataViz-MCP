DataViz MCP — Feature Ideas & Competitive Analysis
========================================================

Goal: make dataviz-mcp more attractive so more people adopt it. Below is
a scan of comparable visualization / code-execution MCP servers, where we
already win, and a prioritized list of what to add.


COMPETITORS SCANNED
-------------------
- antvis/mcp-server-chart   (most popular; 26+ declarative chart types from JSON specs)
- KyuRish/mcp-dashboards    (charts + KPI cards in responsive dashboards)
- datalayer/jupyter-mcp-server (AI edits/executes Jupyter cells)
- StacklokLabs/plotting-mcp (CSV file -> chart)
- Pydantic run-python       (sandboxed python execution)
- mcp-vegalite-server, duckdb-viz (data-file -> chart)


WHAT COMPETITORS HAVE OVER US
-----------------------------
mcp-server-chart (AntV, most popular)
  - Zero-failure rendering (declarative JSON, no code execution to break)
  - Bundled *skill* that teaches the LLM to pick the right chart type
  - Docker deploy

mcp-dashboards
  - 21 themes
  - PNG / PowerPoint / PDF / CSV export
  - Live polling / auto-updating charts
  - Click-to-select that feeds the selection BACK to the AI
  - Drill-down with breadcrumbs

jupyter-mcp-server
  - Persistent kernel state across calls
  - Edit-in-place iteration on cells
  - Auto-adjusts when a cell fails

plotting-mcp / duckdb-viz
  - Direct data-file connectivity (LLM never pastes data into code)


OUR STRUCTURAL ADVANTAGE
------------------------
We execute REAL Python with the full HoloViz stack, so output is a genuinely
interactive app (widgets, linked brushing, streaming) — not a static chart
image or a fixed JSON schema. Plus snippets persist with their own URLs.
Nobody else combines "real interactive apps" + "persistent shareable URLs".

The trade-off / weakness: real code can fail at render time (the whole reason
for the validate/retry work), and we lack the convenience features above
(export, themes, data-file loading, in-place edit).


PRIORITIZED FEATURE IDEAS
-------------------------

TIER 1 — high value, low effort (build on what already exists)

1. update(id, code) tool + snippet version history
   - Today every iteration mints a new snippet/URL. Let the AI (and /add page)
     revise a viz in place, keep the same URL, store versions in SQLite with
     rollback in /admin. "Make the bars horizontal" should not create a new
     page. This is our equivalent of Jupyter-MCP's killer edit-in-place feature.

2. get_status(id) tool — close the render-vs-run gap
   - view_page.py ALREADY stores render-time errors in the DB (error_message),
     but the AI never sees them because show() returned success before the
     browser rendered. A tool that reports "snippet X errored at render time
     with this traceback" makes the AI self-healing for exactly the failure
     class our exec-based validation cannot catch.

3. Export buttons: PNG / standalone HTML / copy code
   - We already have the Playwright screenshot machinery — expose it as a
     download button on /view and /feed. PNG + standalone HTML covers ~80% of
     what mcp-dashboards markets as PPT/PDF export, for near-zero new code.

4. Ship a bundled skill / prompt guide
   - AntV's biggest adoption lever is its chart-visualization skill. A
     dataviz-mcp skill teaching good HoloViz patterns (the sharp edges
     the DEMO_PROMPTS work exposed) would directly cut first-try failures —
     improving the product without touching the server.


TIER 2 — real differentiators, medium effort

5. load_data(path_or_url) — named dataset registry
   - AI registers a CSV/Parquet/URL once; snippets reference it by name
     (pls.data("sales")). Kills the token cost of inlining data, enables
     real-data workflows, and beats the CSV-only servers because you then get
     full pandas/hvplot on it.

6. Dashboard composition
   - /dashboard?ids=a,b,c renders saved snippets in a grid, plus a compose()
     MCP tool. Users already accumulate snippets in the feed — assembling a
     dashboard from them is the natural next step, matching mcp-dashboards
     head-on but with live interactive components.

7. Persistent session state across show() calls
   - Optional shared namespace so an expensive dataframe computed in one
     snippet is reusable in the next — the Jupyter-kernel advantage without
     the notebook.

8. Themes / dark mode
   - Panel ships Material/Fast templates and dark themes natively — expose a
     theme param on show() and a UI toggle. Cheap parity with the "21 themes"
     crowd.


TIER 3 — the moonshot

9. Bidirectional interaction — selections flow back to the AI
   - User clicks points in a scatter; the AI reads the selection
     (get_selection(id) tool or an MCP notification). mcp-dashboards has a
     primitive version; with Panel's linked selections we could do it properly.
     Turns "AI shows you a chart" into "AI and human analyze data TOGETHER in
     the same live view." Nobody has this — it is the demo that makes people
     install it.


IF STARTING WITH THREE
----------------------
#1 (update + versions), #2 (get_status render-error feedback), #3 (export).
They compound with the retry/validation work already in the current PR, reuse
existing infrastructure (SQLite, Playwright, stored render errors), and each is
roughly one PR in size.


LARGE & MULTIDIMENSIONAL DATASET SUPPORT
========================================

There are TWO different problems hiding under "large + multidimensional," and
the HoloViz stack handles them very differently. HoloViz is arguably the BEST
stack in the MCP-viz space for both — but dataviz-mcp currently ships
neither capability in the default path nor tells the AI they exist.

Current state (found in code):
- Default install is minimal: panel, holoviews, hvplot, panel-material-ui only.
  datashader, xarray, dask are NOT installed in the running env.
- pyproject.toml ALREADY has a `pydata` optional-deps group with datashader,
  duckdb, polars, pyarrow, geoviews, plotly, seaborn — the big-data pieces
  exist as opt-in, just not wired into the core path or surfaced to the AI.
- Data enters ONLY by being inlined into the code string (snippet.app). There
  is no file/URL data loader. This is the single biggest limiter for large data.
- Embed size caps (_EMBED_SIZE_CAP=150k, Cowork 25k) cap the OUTPUT html, not
  input. The live /view path streams over websocket and isn't capped.


PROBLEM A — LARGE datasets (millions of rows/points)
----------------------------------------------------
Two separate walls:

1. Rendering wall — SOLVED by the stack, not enabled by default.
   Plain Bokeh chokes above ~50-100k points (every point ships to the browser
   as JSON). HoloViz's canonical answer is Datashader (rasterize/dynspread):
   the server rasterizes millions of points into an image server-side and ships
   only pixels — scales to hundreds of millions of rows. It is ALREADY in the
   pydata group, just not installed by default nor something the AI reaches for.
   HIGHEST-LEVERAGE ADD: install datashader in core (or default env) + teach the
   AI (via bundled skill) to auto-rasterize() above a row threshold. Bonus: a
   rasterized plot is a TINY embed, so it also helps the Cowork/Claude-desktop
   embed-size problem.

2. Input wall — NOT solved, and it's the real blocker.
   Because data is pasted into the code string, you fundamentally cannot get a
   million-row dataset IN. This is exactly the load_data(path_or_url) idea
   (Tier 2 #5) — for large data it's not a nicety, it's the prerequisite. Let
   the AI register a Parquet/CSV/DuckDB/URL once; snippets read it from disk with
   pyarrow/polars/duckdb. No datashader helps if the data can't enter.


PROBLEM B — MULTIDIMENSIONAL datasets (N-D arrays, rasters, cubes)
-----------------------------------------------------------------
Where HoloViz genuinely shines — but the enabling package is MISSING.

- xarray is NOT installed. N-D labeled arrays (climate cubes, image stacks,
  NetCDF/Zarr) are xarray's job, and HoloViews' gridded interface (hv.Dataset,
  hv.Image, hv.QuadMesh) reads xarray natively.
- Killer feature almost for free: hvplot/HoloViews AUTO-GENERATE sliders for
  extra dimensions. A 4-D cube (time x level x lat x lon) becomes an interactive
  map with time and level sliders via ds.hvplot(groupby=[...]) or hv.DynamicMap
  — zero manual widget code. A demo no other viz MCP server can touch.
- Geo/raster -> geoviews (already in pydata) for maps/tiles.

To support it: add xarray (+ optionally netcdf4/zarr for file formats) and
surface it so the AI uses the gridded path instead of melting everything into a
flat DataFrame (which is what makes it fail today).


BOTTOM LINE
-----------
                     | Rendering capability            | Default? | Needed
Large (M+ rows)      | Datashader (in pydata)          | NO       | install datashader in core + load_data() for input + skill guidance to auto-rasterize
Multidimensional N-D | xarray + HoloViews gridded +    | NO       | add xarray (+netcdf/zarr) + surface the gridded path to the AI
                     | auto-sliders                    |          |

The latent capability is there (Datashader for scale, xarray+HoloViews for N-D
are the stack's crown jewels). Turning it on is low-effort and a genuine
differentiator no other viz MCP server can match.


load_data — DESIGN
==================

Core principle: REGISTER ONCE, REFERENCE BY NAME — data never enters the token
stream. The AI registers a dataset, gets back its SCHEMA (not its contents),
then writes code that references it by name. Unlocks the gallery big-data tier
AND improves first-try success (AI sees real column names / dtypes).

1. The MCP tool
   load_data(source: str, name: str | None = None, description: str = "") -> dict
   - source: local path OR http(s) URL.
   - returns a compact "schema card": name, format, n_rows, columns+dtypes, a
     few sample rows, and a usage hint ("df = pls.data('taxi')").
   - the schema card is the whole point: AI knows the data without a single row
     costing tokens.

2. In-code reference — inject a `pls` helper into the exec namespace
   (execute_in_module builds module.__dict__; inject before exec)
   - pls.data("taxi")  -> smart eager load (parquet->pandas, .nc/.zarr->xarray,
                          csv->pandas)
   - pls.path("taxi")  -> cached file path, for manual control (duckdb SQL,
                          dask lazy, custom reader)
   - pls.datasets()    -> list registered datasets
   Give BOTH: data() is the magic 90% path, path() is the escape hatch that
   never guesses wrong.

3. Storage — a registry parallel to the snippets DB
   - new SQLite table `datasets`: name (unique), source, local_path, format,
     n_rows, schema (JSON), size_bytes, description, created_at.
   - new data dir DATAVIZ_MCP_DATA_DIR, default ~/.dataviz-mcp/data/
   - URLs are DOWNLOADED and CACHED into that dir on registration. Important:
     /view re-executes on every render, so a "read the URL each time" design
     would re-download on every browser refresh. Cache once, read local after.

4. Data flow (matches existing client -> endpoint pattern)
   load_data() [MCP proc]
     -> client.py POST /api/data -> DataEndpoint (endpoints.py) [serve proc]
          - resolve path / download URL into data dir
          - sniff format + read CHEAP schema
          - database.py: insert into datasets
          - return schema card
   view render: execute_in_module injects `pls` bound to the datasets registry.
   Single source of truth in the serve process, where code runs.

5. Cheap schema introspection (do NOT read the whole file)
   - Parquet: pyarrow metadata -> schema + num_rows instantly (even 1B rows).
   - CSV: first ~1000 rows for dtypes + estimate row count from file size.
   - NetCDF/Zarr: xr.open_dataset(chunks={}) lazily -> dims/coords/vars/shapes.

6. Cache across renders and snippets
   pls.data() checks pn.state.cache (process-global in serve proc) keyed by
   name+mtime before loading. A 2 GB parquet is parsed ONCE, shared across every
   refresh and every snippet — not re-read each render.

7. Big-data / lazy path
   Eager-loading a billion rows into pandas defeats the purpose.
   - v1: huge case -> AI uses pls.path("taxi") + its own dask/duckdb/rasterize().
   - v2: pls.data("taxi", lazy=True) -> dask/polars-lazy/duckdb relation, and
     Datashader rasterizes it. This is the NYC-Taxi / OSM path.

8. Web UI + config (humans too)
   - /add gets a "dataset" mode: upload a file or paste a URL -> registers it.
   - /admin (or new /data) lists datasets with schema + delete.
   - config: DATAVIZ_MCP_DATA_DIR + DATAVIZ_MCP_MAX_DOWNLOAD_MB cap.

9. Security (be explicit, don't hide it)
   Local-path registration = arbitrary host file read. Fine for a localhost dev
   tool, but: log every registration, cap URL download size, optionally restrict
   to a configured root via an allowlist env var.

Phasing
   v1 (one PR): datasets table + /api/data endpoint + load_data tool +
     pls.data()/pls.path() + parquet/csv schema cards + eager cache. Ship
     pyarrow. Kills the inline-data token wall.
   v2: xarray/zarr multidim cards, lazy=True, Datashader auto-rasterize
     guidance, web UI upload.


BACKLOG — TODAY vs PROPOSED (empirically tested)
================================================

All results below were RUN in the real pixi env (holoviews 1.22, hvplot 0.12,
bokeh 3.8; xarray + datashader NOT installed), not guessed.

MULTIDIMENSIONAL data today — lands on a knife's edge:
  AI writes                                    | Result today
  ---------------------------------------------|----------------------------------
  import xarray / import hvplot.xarray         | HARD FAIL: ModuleNotFoundError
    (the idiomatic path)                        |   (even top-of-file import explodes)
  melt cube -> df.hvplot.image(groupby=[...])  | FAIL: AttributeError — '.image' is a
    (common fallback)                           |   gridded method, melted df is tabular
  hv.Dataset((coords,data),kdims)              | WORKS -> HoloMap with sliders,
    .to(hv.Image,['x','y']) (pure-holoviews)    |   BUT eagerly materializes EVERY frame
                                                |   (OOM/hang on a real cube; xarray path
                                                |    would give a lazy DynamicMap instead)
  Verdict: NOT uniform failure — exactly one path works, but it's the least
  obvious one and it doesn't scale; every obvious path fails.

LARGE data today:
  df.hvplot.points('x','y', rasterize=True)    | FAIL: ModuleNotFoundError datashader
  fallback df.hvplot.scatter on 2M points      | "renders" but embed HTML = 41 MB
                                                |   (cap 150 KB -> 273x over); embed
                                                |   clients fall back to link, live
                                                |   browser chokes on 41MB of point JSON

WHERE THE FAILURE LANDS makes it worse:
  - import xarray / datashader errors are caught at VALIDATION (exec fails ->
    retry pill), so the AI at least learns.
  - BUT the melt AttributeError and the HoloMap OOM happen at RENDER time in
    /view — AFTER show() returned success. Render-vs-run gap: AI thinks it
    worked; user sees a traceback (or a hung tab) in the iframe.

THE BACKLOG (dependency order):
  1. Missing packages (root cause): xarray (+netcdf4/zarr) and datashader not
     installed -> the two most idiomatic paths hard-fail on import.
     -> add them to the core/default env. Cheapest, highest impact.
  2. No data input path: even with the packages, a real cube/raster can't get
     IN (inlined into code string = token wall). -> load_data (design above) is
     the prerequisite for any real multidim/large dataset.
  3. AI doesn't know the gridded/rasterize idioms (reaches for import xarray or
     .hvplot.image first). -> bundled skill/prompt guide: "N-D -> xarray +
     .hvplot(groupby=[...]) for lazy sliders; >100k rows -> rasterize=True."
  4. Render-vs-run blindness: HoloMap-OOM and gridded-shape errors surface only
     in the browser. -> get_status(id) (read stored render error back) so the AI
     can self-heal that class.
  5. Eager HoloMap default: even the working path materializes all frames.
     -> guidance (and maybe a helper) to prefer DynamicMap/groupby.

  Items 1-3 get you from "miserably fails" to "plots correctly."
  Items 4-5 get you from "plots" to "plots at gallery scale."
